## Overview

Die Arbeit des Bedieners lebt heute AUSSCHLIESSLICH im Browser-Speicher.
Ein geleerter Browser, ein anderes Profil, ein zweiter Rechner — und alles
ist weg. Es gibt keinerlei Lade-aus-Datei im Code (geprueft: kein
`FileReader`, kein `input type=file`, kein Datei-Dialog).

Der Export ist KEIN Ersatz: `index.basis.source.html` +
`index.basis.SEvariablen.json` sind das Ergebnis fuer SoftEngine, eine
Einbahnstrasse — der Editor kann daraus nie wieder einen Bauplan machen.

Dieses Paket bringt zwei Menue-Eintraege: **Maske speichern…** (laedt eine
`.json` herunter) und **Maske laden…** (baut die Maske daraus wieder auf).

## Problem Statement

1. **Kein Sicherungsweg.** Vor einem grossen Umbau gibt es kein Zurueck
   ausser Undo — und Undo ueberlebt kein Neuladen.
2. **Kein zweiter Arbeitsplatz.** Die Maske ist an einen Browser gebunden.
3. **Keine zweite Maske.** Der Browser-Speicher hat EINEN Platz; eine neue
   Maske ueberschreibt die alte. Vorlagen aufheben ist unmoeglich.
4. **Kein Weitergeben.** Weder an einen Kollegen noch an einen Agenten laesst
   sich eine Maske reichen.

Steht seit dem 2026-07-21 als Merkposten im Fahrplan („Maske als Datei
speichern/laden fuer Sicherung und zweiten Arbeitsplatz").

## Solution Architecture

**Ein Pruef-Eingang, zwei Quellen.** Das ist der Kern.

Die Lade-Kette (Muell abwehren -> `sanitizeTree` -> Migrationen ->
Notfallkopie) sitzt heute FESTGESCHWEISST im Browser-Speicher-Leser
(`loadFromStorage` liest selbst `localStorage.getItem` und macht alles
Weitere im selben Rumpf). Wuerde der Datei-Weg seine eigene Lade-Kette
bekommen, gaebe es ZWEI Arten, eine Maske einzulesen — und die eine driftet
von der anderen ab. Genau diese Sorte Doppelung hat den Tabellen-Bug
2026-07-24 erzeugt.

Darum zuerst ein reiner Umzug: die Kette wird aus `loadFromStorage`
herausgeloest, sodass beide Leser sie benutzen. Erst danach kommt der
Datei-Weg dazu.

**Alles oder nichts — und zwar ehrlich abgegrenzt** (Codex-Planreview
2026-07-28). Die Zusage lautet: **eine ungueltige Datei aendert am offenen
Stand NICHTS.** Geprueft wird die GANZE Datei, bevor irgendetwas ersetzt
wird; erst wenn Baum UND alle drei Bibliotheken sauber durchkommen, wird
umgeschaltet.

Was NICHT zugesagt werden kann: dass die vier Speicherwege
(Maske + drei Bibliotheken) gemeinsam auf die Platte kommen. Sie schreiben
seit jeher einzeln und entprellt; faellt der Browser-Speicher zwischen dem
ersten und dem dritten Schreiben aus, startet der Editor spaeter mit einem
gemischten Stand. Das ist heute bei JEDER Aenderung so und wird hier nicht
schlimmer. Ein Journal/Zwei-Phasen-Commit waere ein eigener Umbau ohne
belegten Anlass (Regel 10). Immerhin: seit Befund B3 (2026-07-28) meldet ein
gescheitertes Speichern sich in Klartext, statt still zu bleiben.

**Verworfene Eintraege sind ein LADEFEHLER, kein Kollateralschaden.** Die
`sanitize*`-Funktionen der drei Bibliotheken lassen unbrauchbare Eintraege
still aus (`continue`) — richtig fuer einen gewachsenen Browser-Speicher,
falsch fuer eine Datei: eine halb beschaedigte Maskendatei wuerde
„erfolgreich" laden und dabei Datenquellen verlieren. Darum wird beim
Auspacken GEZAEHLT: kommen weniger Eintraege heraus als hineingingen, gilt
die Datei als beschaedigt und wird abgelehnt.

**Und zwar bis in die zweite Ebene** (Codex-Planreview, zweite Runde): eine
Zaehlung nur auf Listenebene sieht nicht, wenn ein Eintrag ZWAR ankommt,
aber innen ausgeduennt wurde — `sanitizeDataSources` verwirft einzelne
FELDER einer Quelle (`dataSources.ts:173`), `sanitizeSourceLinks` verwirft
oder kuerzt einzelne SCHLUESSELPAARE (`sourceLinks.ts:109`). Eine Quelle,
die statt zwoelf Feldern nur noch neun hat, waere der schlimmste Fall: die
Maske laedt, sieht heil aus, und drei Bindungen zeigen ins Leere. Gezaehlt
wird deshalb je Liste UND je Eintrag (Felder je Quelle, Parameter je
Vorlage, Schluesselpaare je Verknuepfung). Jede Abweichung = Datei
beschaedigt.

**Kein halbes Undo.** Siehe Abschnitt 3 — Laden leert die Historie.

## Implementation Details

### 1. Lade-Kette herausloesen (Voraussetzung, kein Selbstzweck)

**File**: `src/state/persistence.ts` (184 Zeilen)

**Current state**: `loadFromStorage()` liest `localStorage`, verteidigt sich
gegen Muell, laeuft durch sechs Migrationen, meldet verworfene Bausteintypen
und rettet unlesbare Staende — alles in EINEM Rumpf.

**Modifications**: Den Teil „aus einem bereits geparsten Objekt einen
brauchbaren Baum machen" in eine eigene Funktion ziehen. `loadFromStorage`
behaelt: lesen, JSON parsen, Notfallkopie bei Wurf — und ruft die neue
Funktion. **Reiner Umzug, KEINE Verhaltensaenderung**; `persistence.test.ts`
muss unveraendert gruen bleiben (eigener Commit-Abschnitt).

**Der Rueckgabewert muss die drei heutigen Nebenwirkungen unterscheidbar
machen** (Codex-Planreview): `null` allein reicht nicht, denn heute loest
„kein Baum" eine Notfallkopie aus, „verworfene Bausteintypen" eine
Bediener-Meldung und `migrated` ein Nachspeichern. Ergebnis darum als
unterscheidbare Form: **gelungen** (mit Baum, `migrated`-Kennzeichen und der
Liste verworfener Typen) ODER **gescheitert** (mit Grund).

**Wer meldet, bleibt beim Aufrufer**: die Notfallkopie legt NUR der
Browser-Speicher-Weg an (eine Datei auf der Platte ist nicht in Gefahr, sie
liegt ja schon beim Bediener). Und Warnungen ueber verworfene Bausteintypen
zeigt der Datei-Weg erst, NACHDEM die ganze Datei durchgekommen ist — sonst
meldet der Editor etwas ueber eine Maske, die er gleich darauf ablehnt.

### 2. Das Dateiformat — die eine Stelle

**File**: `src/state/maskenDatei.ts` (**neu**)

Kennt als EINZIGE Stelle die Form der Datei. Inhalt:

| Feld | Warum |
| --- | --- |
| `art: 'aufbau-editor-maske'` | Erkennungsmarke. Waehlt der Bediener versehentlich `index.basis.SEvariablen.json`, sagt der Editor das in Klartext, statt Unsinn zu laden. |
| `dateiVersion: 1` | Format-Version der DATEI (nicht des Baums). Erlaubt spaeter Aenderungen am Rahmen, ohne zu raten. |
| `schemaVersion` | der Baum-Schemastand — damit die bestehenden Migrationen greifen. |

| `tree` | der Bauplan. |
| `datenquellen`, `relationen`, `verknuepfungen` | die drei Bibliotheken. |

**Nicht drin**: `selectedId` (welcher Baustein gerade markiert ist, ist
Arbeitszustand, kein Inhalt) und die aktive Seite (dito).

**Dateien aus der ZUKUNFT werden abgelehnt** (Codex-Planreview): ist
`dateiVersion` unbekannt oder `schemaVersion` groesser als der eigene Stand,
lautet die Meldung „Diese Datei stammt aus einer neueren Version des
Editors". Sonst wuerde ein aelterer Editor die Migrationen ueberspringen und
anschliessend alles, was er nicht kennt, als „unbekannt" wegwerfen — also
still Arbeit vernichten, die er nur nicht versteht.

- **Packen**: nimmt Baum + die drei Bibliotheken, gibt einen JSON-String.
  Feste Schluesselreihenfolge, zwei Leerzeichen Einrueckung — zwei Speichern
  ohne Aenderung ergeben dieselbe Datei (nachvollziehbare Diffs).
- **Auspacken**: defensiv, wirft NIE. Liefert entweder ein vollstaendiges
  Ergebnis oder einen KLARTEXT-Grund („Das ist keine Maskendatei",
  „Die Datei ist beschaedigt"). Nutzt die Lade-Kette aus Abschnitt 1 fuer
  den Baum und die vorhandenen `sanitize*`-Funktionen der drei Bibliotheken.

### 3. Die ganze Maske in EINEM Zug ersetzen

**File**: `src/state/Editor.ts` (422 Zeilen)

**Current state**: es gibt `clear()` und Einzeloperationen, aber kein
„ersetze den ganzen Baum".

**Modifications**: EINE Methode, die Baum + Auswahl ersetzt. Die aktive
Seite faellt dabei auf die Hauptseite zurueck (die geladene Maske hat andere
Seiten-ids).

**Und sie LEERT die Historie — bewusst kein Undo** (Codex-Planreview
2026-07-28, wichtigster Befund). Die erste Fassung versprach „ein Fehlklick
laesst sich mit Strg+Z zurueckholen". Das waere eine **Falle** gewesen:
`EditorSnapshot` enthaelt nur Baum und Auswahl (`history.ts:10`), die drei
Bibliotheken haben ueberhaupt kein Undo. Strg+Z nach dem Laden ergaebe den
ALTEN Baum mit den NEUEN Bibliotheken — Bindungen zeigen ins Leere, und der
Bediener glaubt, er sei zurueck. Ein halb wiederhergestellter Stand ist
schlimmer als gar keiner.

Undo auf die Bibliotheken auszuweiten waere ein eigener Umbau ohne Anlass
(Regel 10). Also: **Laden ist wie das Oeffnen eines neuen Dokuments** — neue
Maske, leere Historie. Das Sicherheitsnetz ist die Rueckfrage in
Abschnitt 5, die ausdruecklich zum Speichern raet.
Dafuer braucht `Historie` eine Methode zum Leeren (hat sie heute nicht).

**File**: `src/state/DataSourceStore.ts`, `RelationStore.ts`,
`SourceLinkStore.ts`

Je EINE Methode „ganze Liste ersetzen" (heute nur add/update/remove). Sie
laeuft durch dieselbe `sanitize*`-Funktion wie das Laden aus dem
Browser-Speicher, meldet einmal und speichert.

**Ersetzen, nicht zusammenfuehren** (Regel 10): Eine Maskendatei ist ein
vollstaendiger Stand. Zusammenfuehren braeuchte Konfliktregeln
(gleiche id, anderer Inhalt — wer gewinnt?), die niemand angefordert hat.
Der Editor haelt heute ohnehin genau EINE Maske.

### 4. Speichern

**File**: `src/editor/shell/Toolbar.tsx`

`downloadFile()` (Zeile 25) existiert bereits fuer den Export und wird
wiederverwendet — kein zweiter Download-Weg.

- Dateiname mit Datum: `aufbau-maske-JJJJ-MM-TT.json`. Damit sortieren sich
  Sicherungen von selbst und ueberschreiben einander nicht. (Der Dateiname
  ist keine Export-Zusage, das Datum darf hier stehen.)
- Kein Speichern-Dialog: der Browser laedt in den Download-Ordner. Ein
  Datei-Auswahl-Dialog beim Speichern gaebe es nur ueber eine Chrome-eigene
  Schnittstelle — nicht ohne echten Bedarf (Regel 10).

### 5. Laden

**File**: `src/editor/shell/Toolbar.tsx`

- Verstecktes `<input type="file" accept=".json">`, ausgeloest vom
  Menue-Eintrag. Kein neuer Fremdcode.
- **Den Input-Wert nach JEDEM Versuch leeren** (`finally`) — sonst loest die
  Auswahl DERSELBEN Datei kein zweites `change` aus, und der Bediener klickt
  ins Leere, ohne zu verstehen warum (Codex-Planreview).
- **Vorher fragen** — mit einem Text, der zur Bedienung PASST. Ein
  Browser-Rueckfragefenster hat nur OK und Abbrechen; „vorher speichern?"
  waere eine Frage, auf die keiner der beiden Knoepfe antwortet
  (Codex-Planreview, zweite Runde). Also:
  **„Haben Sie den bisherigen Stand gespeichert? Mit OK wird er
  unwiderruflich ersetzt."** Laden ist der einzige Knopf im Editor, der mit
  einem Klick alles ueberschreibt, und seit dem Wegfall des Undo
  (Abschnitt 3) ist diese Rueckfrage das einzige Netz. Bricht der Bediener
  ab, passiert nichts.
- **Feste Reihenfolge** (Codex-Planreview, zweite Runde): Datei lesen ->
  GANZ pruefen -> Rueckfrage -> vollstaendig ersetzen -> erst DANN eine
  Warnung ueber verworfene Bausteintypen zeigen. Andernfalls saehe der
  Bediener „Beim Laden entfernt: …", obwohl er gleich darauf abbricht und
  gar nichts geladen wurde.
- Fehlerfaelle mit Klartext, offene Maske bleibt stehen: keine Maskendatei ·
  beschaedigt · aus einer neueren Editor-Version · Eintraege verworfen ·
  Datei nicht lesbar.
- Nach Erfolg: Auswahl leer, Hauptseite aktiv, Historie leer.

### 6. Was NICHT dazugehoert

- Kein Server, keine Cloud, kein Mehr-Masken-Verwalter (steht als eigener
  Punkt im Fahrplan, „App-Ausbau").
- Keine Aenderung am Export, am Runtime-Buendel oder an einem Baustein.
- Kein Auto-Speichern in Dateien; der Browser-Speicher bleibt der
  laufende Arbeitsstand.

## Technical Considerations

- **Regel 2**: nichts davon kennt einen Bausteintyp; der Baum reist als Baum.
- **Regel 4**: jeder Fehlerweg hat Klartext, nichts scheitert still.
- **Regel 10**: kein Zusammenfuehren, kein Datei-Dialog beim Speichern,
  keine Mehr-Masken-Verwaltung.
- **Deckel 500 Zeilen**: Editor.ts 422 (+ ~20), persistence.ts 184
  (schrumpft eher), maskenDatei.ts neu (~120).
- **Export unberuehrt**: kein Baustein, kein Buendel — der Referenzabzug muss
  OHNE Erneuerung gruen bleiben. Wird er rot, ist etwas falsch.
  **Kein SE-Echttest faellig.**
- **Edge Cases**: Datei aus einer aelteren Editor-Version (Migrationen
  greifen ueber `schemaVersion`) · Datei mit unbekannten Bausteintypen
  (bestehende Meldung „Beim Laden entfernt…" greift) · leere/riesige Datei ·
  Bediener bricht den Datei-Dialog ab · dieselbe Datei zweimal laden
  (muss denselben Stand ergeben) · Bindungen zeigen auf eine Quelle, die in
  der Datei fehlt (Preflight meldet es beim Export, wie heute).

## Test Impact

Keine neue Testart, keine neue Testumgebung (Regel 9, harte Sperre). Die
neuen Faelle sind pure Funktionen und laufen in bestehenden Dateien mit:

- Packen -> Auspacken ergibt denselben Baum und dieselben drei Bibliotheken.
- Zweimal packen ohne Aenderung ergibt denselben String.
- Auspacken wehrt ab: fremde Datei (SEvariablen.json), kaputtes JSON,
  fehlende `art`-Marke, leerer String — je mit Klartext-Grund, nie ein Wurf.
- Eine Datei mit altem `schemaVersion` wird beim Auspacken migriert.
- Eine Datei mit ZU NEUEM `schemaVersion` bzw. unbekanntem `dateiVersion`
  wird abgelehnt (nicht halb geladen).
- Eine Datei mit einer kaputten Datenquelle unter mehreren wird ABGELEHNT
  (Zaehlprobe), nicht still um diese Quelle erleichtert.
- Dasselbe eine Ebene tiefer: eine Datei, bei der EINE Quelle ein kaputtes
  Feld hat bzw. eine Verknuepfung ein kaputtes Schluesselpaar, wird ebenfalls
  abgelehnt — der Eintrag kommt ja durch, nur ausgeduennt.
- Historie: Undo/Redo erzeugen, dann Maske ersetzen — danach muessen
  `canUndo` und `canRedo` beide falsch sein (kein halber Rueckweg).
- `persistence.test.ts` bleibt nach dem Umzug (Abschnitt 1) unveraendert gruen.
- `referenzabzug.test.ts` bleibt OHNE Erneuerung gruen (Export unberuehrt).

Klickanleitung fuer den Nutzer statt Agenten-Browsertest.
