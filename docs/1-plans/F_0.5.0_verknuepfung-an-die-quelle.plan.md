# F_0.5.0 — Verknüpfung wandert vom Baustein an die Datenquelle

Stand: 2026-07-30 · Basis: v0.4.0 (`5c97056` + Design-Commits) · Status: **Plan, kein Go**

## Anlass

Nutzer-Einwand 2026-07-30, wörtlich: *„WIESO muss unbedingt zweite datenquelle
dafür? wieso muss ein baustein überhaupt 2 datenquellen dafür haben?"*

Er hat recht. Die Frage zerfällt in zwei, und nur eine davon hat eine
zwingende Antwort.

**Zwingend: verknüpft werden MUSS.** SoftEngine liefert keine
zusammengesetzten Daten. Jeder SEFILELOOP-/ERPAPICALL-Eintrag ist eine flache
Tabelle. Beleg aus der echten, laufenden Empfangs-Maske
(`docs/chef-maske/empfang/`): fünf getrennte Quellen (ADR, IDBID0001
Terminplaner, IDBID0004 Kundenhaustiere, BEL, ERPAPICALL LIEFERADRESSE.GET),
und die Maske führt sie **von Hand in JavaScript** zusammen —
`index.basis.source.html:2589`:
`loadRows('Haustiere').filter(… getField(r, FELD.HT.adr) === TM.adr)`.
Eine einzige Terminkarte (ab `:1620`) zieht aus vier dieser Tabellen.
Das Feature steht also auf einem echten Fall (Regel 10 erfüllt).

**Nicht zwingend: WO die Regel eingestellt wird.** Dass sie seit v0.3.0 am
Baustein hängt, war eine Entscheidung, kein SE-Zwang. Sie ist die schlechtere:
in der echten Maske brauchen Kanban-Karte, Tagesagenda, Kundenliste und
Termin-Dialog *dieselbe* Verknüpfung Termin→Adresse. Am Baustein heißt das
viermal dieselbe Schlüsselregel eintippen — und viermal die Chance, sie
falsch einzutippen, mit einem still leeren Feld als einziger Rückmeldung.

## Ziel

Die Schlüsselregel gehört an die Datenquelle. Ein Baustein hat wieder
**genau eine** Quelle. In der Kommandozentrale einmal sagen „Termine, dazu die
Adresse über Adressnummer" — jeder Baustein, der Termine wählt, hat die
Adressfelder.

**Nicht-Ziele:** ERPAPICALL (eigenes Paket danach), Quellen-Arten als Daten
statt Code (offene Frage, eigenes Paket), mehrstufige Ketten (s. u. — bleibt
bewusst offen, wird durch diesen Umbau aber erst möglich).

## Bekannte Decke, die dieser Umbau NICHT hebt (Befund 2026-07-30)

Beim Nachlesen der echten Maske gefunden, gehört auf den Tisch: sie verknüpft
**zweistufig**. `petMasterOf` (`empfang/index.basis.source.html:1565`) sucht
die Haustier-Stammzeile (ERPAPICALL) über `lfanr` — und dieses Feld kommt
nicht vom Termin, sondern aus der *Kundenhaustiere*-Zeile
(`petMasterForVisit`, `:1576`). Kette: Termin → Kundenhaustiere (über die
Satznummer des Termins, `visitPetList` `:1554`) → Haustiere. Zusätzlich gibt
es einen Namens-Stichentscheid unter mehreren Treffern (`:1571`) — den kann
eine Schlüsselpaar-Regel gar nicht ausdrücken.

Ehrlich dazu: **das kann der Editor heute auch nicht**, weder am Baustein noch
an der Quelle. Der Umbau macht es also nicht schlechter. Er macht die zweite
Stufe aber erst *sauber nachrüstbar*: an der Quelle heißt die Kette
„Kundenhaustiere hängt an Termine, Haustiere hängt an Kundenhaustiere" — jede
Regel dort, wo sie hingehört. Am Baustein wäre dieselbe Kette eine flache
Liste mit Querverweisen untereinander. Nachrüsten bleibt ein eigenes Paket
(Regel 10 — erst wenn er die Maske wirklich nachbaut).

## Was sich NICHT ändert

- **Bindungsform** `quelle::feld` — ein Baustein bindet weiter an
  `kundenhaustiere::78_30`. Kein Baustein-Code, kein Feld-Picker-Umbau.
- **Export-Form**: weiterhin N SEFILELOOP-Einträge + Zusammenführung in JS.
  Die SEvariablen-JSON bleibt byte-gleich; nur das HTML verliert die
  `weitereQuellen`-Attribute (kleinere Maske).
- `SchluesselPaar`, `vollstaendigePaare`, `MAX_SCHLUESSELPAARE`,
  `quelleBrauchbar` — dieselbe Logik, nur ein anderer Träger.
- Die „nicht gefunden = leer, nie Zeile weg"-Regel (Nutzer 2026-07-25).

## Schritte

### 0. Zwischenstand sichern
Der Datenquellen-Umbau (Vorlage/Einfügen/Einzeln + `bausteineMitQuelle`-Fix)
liegt ungespeichert da, Bündel grün. Erst als eigener Commit ablegen — sonst
mischt sich ein UI-Umbau mit einer Modelländerung in einen unlesbaren Diff.

### 1. Modell (`core/data/`)
`BausteinQuelle` → `AngehaengteQuelle` (identische Form: `quelleId` +
`keyPairs`), Träger wechselt:

```ts
interface DataSource {
  …
  // Quellen, deren Felder zu jeder Zeile DIESER Quelle mitgeliefert werden,
  // gefunden über die Schlüsselregel. Eine Stufe, kein Anhang am Anhang.
  angehaengt?: AngehaengteQuelle[]
}
```

Weg: `WEITERE_QUELLEN_PROP`, `QUELLEN_DEFAULTS` (die Prop an jedem Baustein),
`weitereQuellenAus` (wird zu `angehaengteAus`, gelesen aus der Quelle).
`quellenAufloesen(sourceId, weitereRoh, bibliothek)` →
`quellenAufloesen(sourceId, bibliothek)`.

Neu in `sanitizeDataSources`: `angehaengt` prüfen wie bisher die Prop.
**Zyklen abweisen** (A hängt an B hängt an A) — bei einer Stufe genügt
„eine Quelle darf sich nicht selbst anhängen", muss aber dastehen.

### 2. Laufzeit (`blocks/shared/fremdeQuellen.ts`)
Liest die Regel aus `FF_DATA_SOURCES` statt aus dem Element-Attribut. Wird
dabei **einfacher und schneller**: der Nachschlag-Index entsteht einmal pro
Quelle statt einmal pro Element — heute baut jede Kanban-Spalte ihren eigenen.

### 3. Export (`export/exportMask.ts`, `preflight.ts`)
`collectDataSources` folgt `angehaengt` der gesammelten Quelle statt der
Block-Prop. Preflight prüft die Regel an der Quelle. Referenzabzug ändert
sich (Attribute fallen weg) → `npx vitest run -u`, Diff im Commit sichtbar.

### 4. Bedienung
- **Raus:** `editor/inspector/QuellenListe.tsx` (Schlüsselpaare am Baustein).
  Der Inspector zeigt wieder eine Quelle — eine Auswahlliste.
- **Rein:** Abschnitt „Angehängte Quellen" in `DataSourceForm` +
  `DatenquellenBereich`-Detail: welche Quelle, welche Feldpaare, in
  Klarnamen. Liste in der Kommandozentrale zeigt den Anhang mit an.

### 5. Migration (`state/maskenDatei.ts`, `persistence.ts`)
Maskendatei-Version **2 → 3**. Bestand trägt `weitereQuellen` in Block-Props.

Vorschlag: **umheben statt verwerfen.** Beim Laden je Baustein die Prop lesen
und an *seine erste Quelle* hängen; Prop danach fallen lassen.
Konfliktregel bei zwei verschiedenen Regeln für dasselbe Quellenpaar:
**erste im Baum gewinnt**, der Rest wird verworfen — deterministisch, und der
Fall ist bei einer nie in SE getesteten v0.3.0 hypothetisch.
`keinVerlust` in `maskenDatei.ts` muss die Prop wie damals `verknuepfungen`
ausdrücklich durchlassen, sonst schlägt der Verlust-Wächter an.

Falls das Umheben beim Bauen unsauber wird: **verwerfen mit Ansage**
(wie `verknuepfungen`), begründet im Commit.

### 6. Prüfen
Bündel (`tsc -b`, `eslint src`, `check:regeln`, `check:runtime`,
`check:docs`, `test`). Bestehende Tests in `sourceLinks.test.ts`,
`quellenOps.test.ts`, `datenquellen.test.ts`, `preflight.test.ts`,
`maskenDatei.test.ts` wandern auf den neuen Träger — **keine neue Testart**
(harte Sperre 2026-07-28).
Gegenprobe: Migration absichtlich brechen → Test rot → zurückstellen.

## Offene Punkte für die Zweitmeinung

1. Migration umheben (Konflikt: erster gewinnt) oder verwerfen?
2. Braucht ein Baustein je einen Anhang, den eine *andere* Verwendung
   derselben Quelle nicht will? Dann wäre die Quelle der falsche Träger und
   der ganze Umbau falsch. Gegen-Beleg aus der echten Maske gesucht.
3. Wenn die zweite Stufe (s. „Bekannte Decke") ohnehin kommt: sollte
   `angehaengt` das Modell schon jetzt rekursiv zulassen und nur die
   Bedienung eine Stufe anbieten — oder ist das Bauen auf Verdacht (Regel 10)?
4. Bleibt die Verlust-Prüfung `keinVerlust` beim Umheben ehrlich, oder
   verdeckt eine Ausnahme dort echten Datenverlust?
